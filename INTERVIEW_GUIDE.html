The Problem Story
Emotional Anchoring
The "blind push" problem
A team ships a RAG system. It works in demo. Three weeks later, users complain answers are vague and off-topic. The team has no idea what changed — or when it changed. They added a new document corpus, tweaked the prompt twice, and updated the model. Which one broke it? They have no data. They eyeball a few answers and push another guess.

This is the default state of most LLM deployments. Deploying an LLM is not the finish line — it's the starting gun for monitoring.

Software teams solved this 20 years ago: version control, CI/CD, metrics, alerts. LLM teams are repeating the same mistakes from the pre-DevOps era. This project applies those solved patterns to the LLM layer:

  • Prompt changes are versioned in YAML and git — auditable like code
  • Quality regressions are caught statistically, not by eyeballing
  • Drift is detected automatically before users notice
  • Every inference call is instrumented — latency, tokens, error rate
Don't say: "I built a dashboard to monitor LLMs."
Say: "I built the infrastructure that lets teams catch prompt regressions before they reach users."

What LLMOps Is — The Mission Control Analogy
Prior Knowledge Anchoring
Analogy: NASA Mission Control

When NASA launches a rocket, they don't fire it and walk away. Mission Control watches telemetry in real time — thrust, trajectory, temperature. They have threshold alerts. When a reading drifts outside the expected range, an alarm fires before the rocket goes off-course.

LLMOps is Mission Control for your LLM.
The rocket = your LLM system.
Telemetry = latency, token counts, faithfulness scores.
Trajectory drift = quality regressions across prompt versions.
Threshold alerts = faithfulness < 0.70, latency > 3000ms.

What the toolkit monitors

  • Per-call: latency, token counts, error rate
  • Per-run: faithfulness, relevancy, context precision
  • Cross-run: drift (rolling z-score vs. baseline)
  • On change: A/B test before deploying new prompts

Architecture Walkthrough
Method of Loci

Memory anchor: walk through a building with 7 rooms. Each room = one system component. Visualize it physically.

1
Prompt Registry (The Library)
What:
YAML files in prompts/ directory. Each file = one versioned prompt template.
Why YAML:
Git-trackable. Human-readable. git blame shows who changed what and when. PR-reviewable.
Key operation:
registry.render("rag_qa_v1", context=..., question=...) — raises ValueError for missing variables.
2
Inference Gateway (The Toll Booth)
What:
Single entry point for ALL LLM calls. Every call is instrumented — nothing bypasses it.
Prometheus metrics:
llm_requests_total (Counter)
llm_latency_seconds (Histogram, 6 buckets)
llm_tokens_total (Counter, prompt + completion)
llm_error_rate (Gauge, rolling 100-req)
SDK choice:
groq SDK directly (not LangChain) — exact token counts from response.usage.
3
MLflow Tracker (The Ledger)
What:
Logs every evaluation run as an MLflow experiment run. One experiment per project, one run per eval.
Key pattern:
Prompt version stored as run TAG (not param) — keeps hyperparameter space clean. Template text logged as artifact for auditability.
Context manager:
with tracker.start_run("eval-v1"): — run auto-ends on exit.
4
Drift Detector (The Seismograph)
What:
Rolling window z-score comparison. Baseline = first N runs (locked). Window = latest N runs (rolling).
Formula:
z = (window_mean − baseline_mean) / baseline_std
|z| > 1.5σ → DRIFT
Direction:
"degraded" if score drops, "improved" if rises (both trigger — unexpected improvements also warrant investigation).
5
Alert Engine (The Pager)
What:
Evaluates AlertRule definitions against incoming metric dicts. Maintains active/history state.
Cooldown:
Default 300s per rule — prevents alert storms on repeated metric evaluations.
Lifecycle:
FIRING → RESOLVED (auto when metrics recover, or manual acknowledge_alert()).
6
A/B Test Runner (The Referee)
What:
Runs the same question set through two prompt versions. Applies Mann-Whitney U for significance.
Key output:
p-value, winner, rank-biserial effect size (range −1 to +1), recommendation string.
CI mode:
--fail-on-regression: exits with code 1 if B is significantly WORSE than A — blocks the merge.

Three Technical Pillars
Rule of Three
Pillar 1: Drift Detection
z = (μ_window − μ_baseline) / σ_baseline
|z| > 1.5σ → DRIFT
Why z-score not threshold? A model scoring 0.68 faithfulness consistently shouldn't alert at 0.69. Z-score adapts to your baseline variance — if the model is rock-solid, a 0.02 drop is suspicious; if it's naturally noisy, it isn't. This is how Arize AI and Fiddler AI detect drift in production.
Pillar 2: A/B Testing
Mann-Whitney U
p < 0.05 → significant
effect_size = 1 − (2U / n₁n₂)
Why Mann-Whitney not t-test? Faithfulness scores (0.0–1.0) are bounded and non-normal. t-test assumes normal distribution — incorrect here. Mann-Whitney is non-parametric: it ranks all scores together and tests if one group tends to have higher ranks. Works correctly with n=5–10 samples.
Pillar 3: Prometheus Metrics
Counter, Histogram, Gauge
/metrics endpoint
label: prompt_name + status
Why Prometheus client? One pip install produces a proper /metrics endpoint that Prometheus and Grafana scrape in production. No infrastructure change needed to go from demo to production — just point your Prometheus config at the endpoint. Labels by prompt_name enable per-prompt dashboards.

The Evaluation Metrics (same signal as RAGAS, zero dependency conflicts)

Metric Method Cost Formula
Context Precision Jaccard similarity, stopword-filtered Free (pure Python) relevant_chunks / total_chunks where Jaccard ≥ 0.05
Faithfulness LLM judge (Groq Llama) ~1 API call 1 − (unsupported_claims / total_claims)
Answer Relevancy Embedding cosine similarity Free (local model) mean(cosine(embed(synthetic_q_i), embed(original_q)))
Overall Score Weighted composite — 0.3×precision + 0.4×faithfulness + 0.3×relevancy

Design Decisions as Contrast Pairs
Contrast Effect

The brain remembers contrasts better than isolated facts. For each decision, memorize what you didn't do and why.

Decision 1: Prompt storage
NOT THIS
Database / SQLite
Opaque. "Who changed this prompt?" requires a database query. Not PR-reviewable. Hard to roll back. Separate from your codebase.
THIS
YAML files in git
git blame prompts/rag_qa_v1.yaml shows who, when, and why. PR-reviewable. Rollback = git revert. Lives with the codebase. This is how Anthropic and Glean manage prompts in production.
Decision 2: Drift detection method
NOT THIS
Fixed threshold ("alert if < 0.70")
Brittle. A model that always scores 0.68 fires on every run. A model that usually scores 0.95 but drops to 0.72 doesn't fire. The threshold doesn't adapt to baseline variance.
THIS
Z-score against rolling baseline
Adapts to your specific model's variance. Same math used by Arize AI, Evidently, and Fiddler for production ML monitoring. Catches meaningful regressions without crying wolf on natural noise.
Decision 3: Statistical test for A/B
NOT THIS
Welch's t-test
Assumes normal distribution. Faithfulness scores are bounded [0,1] and often bimodal (very faithful or very not). Incorrect for n=5–10 samples. The t-test p-value is meaningless here.
THIS
Mann-Whitney U (non-parametric)
Makes no normality assumption. Works on ranks, not values. Correct for bounded non-normal distributions at small sample sizes. Plus: rank-biserial correlation gives interpretable effect size.
Decision 4: LLM SDK choice
NOT THIS
langchain-groq
Fine for chains, but wraps token counting inconsistently. Adds ~15 transitive dependencies for a gateway that just needs to call an API and count tokens exactly.
THIS
groq SDK directly
response.usage.prompt_tokens is exact, always. Minimal surface area. Shows provider SDK knowledge beyond LangChain abstractions. Prometheus metrics per prompt_name label work cleanly.
Decision 5: MLflow run tags vs. params
NOT THIS
Log prompt version as MLflow param
Parameters are treated as hyperparameters — they pollute the param space and break the "Compare Runs" view in MLflow UI (it tries to plot them as numeric axes).
THIS
Log prompt version as MLflow tag
Tags are metadata — they appear in the runs table but don't interfere with metric comparison charts. prompt.name and prompt.version as tags is the idiomatic MLflow pattern.
Decision 6: Prometheus metrics registry
NOT THIS
Metrics inside the class __init__
Gradio reloads modules on change (hot-reload). Re-importing triggers ValueError: Duplicated timeseries from Prometheus — the Counter is registered twice.
THIS
Metrics at module level with try/except
Module-level globals are initialized once. The try/except pattern catches the duplicate registration and retrieves the existing collector. Survives Gradio hot-reload and test suite re-imports cleanly.

Hard Interview Q&A
Active Retrieval · Spaced Repetition
Question Answer
How is your drift detection different from just setting an alert threshold? A fixed threshold (e.g., "alert if faithfulness < 0.70") is brittle — it fires on every natural variance below that line, and misses meaningful drops above it. Z-score compares current performance against your specific baseline distribution. A model that consistently scores 0.68 won't alert at 0.69. A model that usually scores 0.95 but suddenly drops to 0.72 will alert, because that's 1.5+ standard deviations below its baseline. This is how production ML monitoring works (Arize, Evidently, Fiddler).
Common trap: don't say "I set the threshold to 1.5 sigma" — say "I set the z-score threshold to 1.5σ, which means a 1.5 standard deviation deviation from the baseline distribution."
Why Mann-Whitney U instead of a t-test for your A/B comparison? LLM quality scores are bounded [0, 1] and often non-normal — they can be bimodal (questions where the model is either very faithful or completely wrong, with few values in between). The t-test assumes normality, which is incorrect here. Mann-Whitney U is non-parametric: it ranks all scores from both groups together and tests whether one group's ranks tend to be higher. It makes no distribution assumption and works correctly at small sample sizes (n=5–10), which is typical for LLM evaluation sets (they're expensive to run). I also compute rank-biserial correlation as an effect size, which gives a meaningful -1 to +1 number for "how different are these distributions."
What's the difference between your Prometheus gauge, counter, and histogram? Why each? Counter for cumulative counts that only go up: llm_requests_total (total calls), llm_tokens_total. You can compute rate() from a counter in Grafana.

Histogram for latency: llm_latency_seconds with 6 buckets (0.5, 1.0, 2.0, 3.0, 5.0, 10.0s). Histograms let you compute percentiles (p95, p99) in Grafana — critical for SLA monitoring.

Gauge for point-in-time values that go up and down: llm_error_rate (rolling 100-req fraction) and llm_active_requests (in-flight count). Gauges represent current state, not cumulative totals.
How does your CI pipeline prevent a bad prompt from reaching production? The GitHub Actions workflow has two jobs: unit tests run on every PR (fast, no API key). On merge to main, an integration job runs the A/B test CLI with --fail-on-regression. This compares the new prompt version against the baseline using Mann-Whitney U on 5 test questions. If the new prompt is statistically significantly worse (p < 0.05 AND mean_new < mean_baseline), the script exits with code 1, which fails the CI job and blocks deployment. The MLflow run is uploaded as a GitHub artifact, so you have a permanent record of every evaluation that ran in CI.
Be ready to explain: "What if 5 questions isn't enough for statistical power?" — answer: "At n=5, the minimum detectable p-value with Mann-Whitney is ~0.05. For larger differences this works; for subtle ones, we'd need more questions. The tradeoff is evaluation cost vs. sensitivity."
Why log prompt version as an MLflow tag instead of a parameter? MLflow's "Compare Runs" view treats parameters as hyperparameters — it tries to show them in a parameter importance chart and as axes for parallel coordinate plots. A string like "rag_qa_v1" breaks those numeric visualizations. Tags in MLflow are metadata: they appear in the runs table as filterable columns, support string values, and don't interfere with metric comparison charts. The pattern prompt.name and prompt.version as tags maps directly to how ML teams tag model versions in production MLflow deployments.
How does your alert engine handle alert storms (same alert firing repeatedly)? Each AlertRule has a cooldown_seconds field (default 300s = 5 minutes). When a rule fires, its name is recorded in _last_fired with the epoch timestamp. On each subsequent evaluate() call, I check if the time since last fire is less than cooldown_seconds. If it is, the rule is skipped even if the metric is still bad. This prevents a metrics collection loop running every 10 seconds from generating 360 duplicate "faithfulness_low" alerts per hour. The alert remains "FIRING" in the active state — it just doesn't generate new AlertEvent objects. Resolution happens automatically when the metric recovers, or manually via acknowledge_alert().
Why use the groq Python SDK directly instead of langchain-groq? Two reasons. First: exact token counts. The groq SDK returns response.usage.prompt_tokens and response.usage.completion_tokens directly from the API response. LangChain wraps this inconsistently — sometimes it re-tokenizes locally, sometimes it relies on callback handlers, and the numbers can differ from the actual API billing. For a cost-tracking component, exact counts matter. Second: minimal dependency surface. The gateway is a thin instrumentation layer — it shouldn't pull in 15 LangChain transitive dependencies. The groq SDK is a single focused package. This also demonstrates that I understand the provider API directly, not just the LangChain abstraction over it.
How would you scale this to a multi-tenant enterprise deployment? Several extensions: (1) The Prometheus labels already have prompt_name — add tenant_id as a second label for per-tenant dashboards without code changes. (2) MLflow supports remote tracking servers (Postgres + S3) — change MLFLOW_TRACKING_URI to point there. (3) The alert engine rules are in-memory now; replace with a Redis-backed store for distributed deployments. (4) The inference gateway is stateless (Prometheus metrics use internal locks) — it runs correctly behind a load balancer. (5) For audit compliance, the YAML prompt registry is already git-tracked — add branch protection rules requiring approval before prompt changes merge to main.

Active Retrieval Exercise — Cover the answer column and answer these out loud

  1. What is z-score drift detection and why is it better than a fixed threshold?
    Z-score compares window mean vs. baseline mean in units of baseline standard deviation. Adapts to your model's natural variance.
  2. Why Mann-Whitney U and not a t-test?
    LLM scores are bounded, non-normal, and we have small samples (n=5-10). Mann-Whitney is non-parametric — no normality assumption.
  3. What is the difference between a Prometheus Counter, Histogram, and Gauge?
    Counter: only goes up (requests, tokens). Histogram: records distributions (latency, enables percentiles). Gauge: current state up/down (error rate, active requests).
  4. Why YAML prompts instead of a database?
    Git-trackable, PR-reviewable, auditable with git blame, rollback = git revert. Lives with the codebase.
  5. What prevents the CI pipeline from deploying a bad prompt?
    --fail-on-regression exits with code 1 if new prompt is significantly worse (Mann-Whitney p<0.05 + lower mean), blocking the CI job.
  6. What is alert cooldown and why does it matter?
    Cooldown_seconds prevents the same rule from re-firing within that window. Stops alert storms when a metrics loop runs every 10 seconds.
